A história da aula: por que começar pelo IP da NBA?

A pergunta da aula. Todo mundo já digitou um endereço no navegador e viu a página aparecer. A aula inteira responde a uma pergunta só: o que acontece entre apertar Enter e a página aparecer? Para responder, vamos seguir um pedido de verdade, do começo ao fim, e usar o terminal do Kali para enxergar cada etapa.

Por que o site da NBA? Qualquer site serviria. O www.nba.com é um bom exemplo porque é conhecido e, num endereço só, mostra quase tudo o que a aula quer ensinar:

  • o nome dele passa por apelidos até chegar a um endereço (tópico 1);
  • quem entrega a página não é a NBA, e sim uma empresa de entrega de conteúdo, a Akamai, com um servidor perto de nós (tópicos 1 e 3);
  • o servidor recusa o pedido de um programa que não parece navegador (tópico 4);
  • ele só aceita conversa com cadeado (HTTPS) e tem um certificado que dá para examinar (tópico 4).

Por que começar pelo endereço IP? Porque é a primeira coisa de que o computador precisa.

  • Na internet, cada computador é encontrado por um número, o endereço IP (por exemplo, 23.201.217.31). Ele funciona como o endereço de uma casa: sem ele, o carteiro não sabe para onde levar a carta.
  • Nós lembramos nomes (www.nba.com), mas a rede só entende números. Então, antes de qualquer outra coisa, o computador precisa descobrir: "qual é o número de www.nba.com?".
  • Por isso a viagem começa pelo DNS, o serviço que traduz o nome no número. Sem o IP, nada do resto acontece: não há com quem abrir a conversa nem caminho a seguir.

As 5 paradas da viagem. Cada parada usa o que a anterior entregou: o DNS entrega o IP; o TCP/IP usa esse IP para abrir a conversa; os roteadores levam os pacotes até lá; o HTTP faz o pedido dentro dessa conversa; e, no fim, trocamos de lado e viramos o servidor.

O terminal é uma janela onde se conversa com o computador por texto: você digita um comando, aperta Enter e lê a resposta. Dentro do contêiner, cada linha começa com o prompt, algo assim:

Neste roteiro, os blocos de comando mostram só o que se digita, sem o prompt.

Como ler um comando

ping   -c 4   www.nba.com
│      │      │
│      │      └─ argumento: SOBRE O QUE o comando age
│      └─ opção (ou flag): COMO ele deve agir. Começa com - ou --
└─ comando: O QUE fazer (o nome de um programa)
  • Opções curtas têm um traço e uma letra (-c). Várias podem ser juntadas: -zv é o mesmo que -z -v. Opções longas têm dois traços e uma palavra (--build).
  • Algumas opções recebem um valor logo depois: em -c 4, o 4 pertence ao -c.
  • Maiúsculas e minúsculas são diferentes. curl -I e curl -i fazem coisas diferentes.
  • O espaço separa as partes. Se um valor tem espaços ou símbolos, vai entre aspas: "Mozilla/5.0".
  • Em arquivos de configuração, linhas que começam com # são comentários: o sistema ignora.

Tópico 1 — DNS

O que é DNS?

Onde estamos na viagem: você digitou www.nba.com e apertou Enter. Antes de qualquer coisa, o computador precisa do endereço IP do site, porque é por número que os computadores se encontram.

O que é. O DNS (Domain Name System, sistema de nomes de domínio) é a "agenda de contatos" da internet. No celular, você guarda o contato pelo nome ("Mãe") e o aparelho disca o número. Na internet, você digita o nome (www.nba.com) e o DNS devolve o número (23.201.217.31).

Como funciona, em uma frase: o seu computador pergunta a um servidor DNS "qual é o IP de www.nba.com?", e ele responde. Se não souber, ele mesmo pergunta a outros servidores, em etapas (é o que o dig +trace mostra no passo 7).

Palavras que vão aparecer:

  • domínio: o nome de um site (nba.com). Lê-se da direita para a esquerda: .com → nba → www.
  • servidor DNS (resolvedor): o computador que responde às perguntas de nome. O seu está anotado no arquivo /etc/resolv.conf (passo 1).
  • registro: cada informação guardada no DNS, como A (o endereço IPv4) ou CNAME (um apelido). Ver o slide 1.3.
  • cache: a memória das respostas recentes, para não perguntar de novo a cada clique.

Por que importa para segurança: se alguém consegue fazer o DNS responder errado, você vai para o endereço errado achando que está no certo. É a base de vários golpes.

Desafio: Descubra o endereço IP do www.nba.com e quem respondeu a sua pergunta.

Para que serve a pasta /etc? É onde ficam as configurações do sistema e dos programas. Quando se quer mudar como o Linux se comporta, quase sempre a resposta está num arquivo de /etc. Só o administrador (root) pode alterá-los.

Que tipos de arquivo há lá? Quase todos são arquivos de texto simples, que se leem com cat e se editam com vim ou nano. Muitos terminam em .conf; outros não têm extensão (no Linux, a extensão é só parte do nome). Programas maiores ganham uma subpasta própria, como /etc/ssh/ e /etc/apt/. Exemplos:

ArquivoO que guarda

O que o resolv.conf guarda? A quem o computador deve perguntar para resolver nomes (daí o nome, de resolver). A linha principal é nameserver IP: o servidor DNS. Pode haver mais de uma (se o primeiro não responde, o sistema tenta o próximo), além de linhas search (domínio completado automaticamente) e options (ajustes).

Por que precisamos dele? Todo programa que recebe um nome (ping www.nba.com, curl, o navegador) precisa trocá-lo por um IP antes de qualquer coisa. É neste arquivo que o sistema descobre a quem perguntar. Sem ele, só funcionariam endereços IP digitados à mão. Também é um ponto sensível: quem altera o resolv.conf de uma máquina escolhe quem responde às perguntas DNS dela, e pode mandá-la para sites falsos.

Tópico 2 — TCP/IP

O que é TCP/IP?

Onde estamos na viagem: o DNS já nos deu o IP da NBA (23.201.217.31). Agora o computador precisa conversar com esse endereço.

O que é. TCP/IP é o nome do conjunto de regras (os protocolos) que todos os computadores da internet seguem para trocar dados. Protocolo é um combinado: "eu falo assim, você responde assado". As duas regras principais dão o nome:

  • IP (Internet Protocol): dá um endereço a cada computador e leva cada pedaço de dado até o endereço certo. É o envelope, com remetente e destinatário.
  • TCP (Transmission Control Protocol): abre uma conversa confiável entre dois programas. Confere se tudo chegou, na ordem certa, e reenvia o que se perdeu. É como uma ligação telefônica: primeiro alguém atende, depois se conversa.

Pacotes. Nada viaja inteiro: os dados são picotados em pacotes, pequenos pedaços que levam o IP de origem e o de destino. Do outro lado, o TCP remonta tudo.

Portas. Um computador roda vários programas de rede ao mesmo tempo. A porta é o número que diz qual programa deve receber o pacote: o IP é o prédio; a porta é o apartamento. O site da NBA atende na porta 443 (HTTPS).

Por que importa para segurança: toda conversa tem 4 números: o seu IP e a sua porta, o IP e a porta do outro lado. Saber lê-los (com o ss, no passo 4) é saber com quem uma máquina está falando.

Desafio: Prove que o seu Kali consegue abrir uma conversa TCP com o servidor da NBA e mostre essa conversa acontecendo: de qual IP e porta ela sai, e a qual IP e porta ela chega.

Tópico 3 — Roteadores

O que é um roteador?

Onde estamos na viagem: sabemos o IP da NBA e como abrir a conversa. Mas o servidor não está ligado por um fio direto ao nosso computador. Como os pacotes chegam até lá?

O que é. Um roteador é um equipamento que liga redes diferentes e, para cada pacote que chega, decide para qual equipamento mandá-lo em seguida. A "caixinha" do Wi-Fi da sua casa é um roteador: ela liga a rede da casa à rede do provedor.

Como o pacote chega: nenhum roteador conhece o caminho inteiro. Cada um só sabe o próximo passo, como um GPS que só conhece o próximo cruzamento. O pacote vai pulando de roteador em roteador, e cada pulo é um salto (hop). Até o servidor da NBA, o traceroute do passo 3 mostra cerca de 10 saltos.

Palavras que vão aparecer:

  • rede local: as máquinas "do lado", na mesma casa ou no mesmo escritório. Entre elas, a conversa é direta.
  • gateway (porta de saída): o primeiro roteador, para onde vai tudo o que não é da rede local (passo 1).
  • provedor: a empresa que leva a internet até você (Vivo, Claro…). A internet é uma rede de redes: a de casa, a do provedor, as internacionais e a da Akamai.

Por que importa para segurança: os pacotes passam por equipamentos de várias empresas. Se a conversa não estiver protegida, qualquer um desses pontos pode ler o conteúdo. É o gancho para o HTTPS.

Desafio: Descubra qual é o primeiro roteador do seu caminho (o seu gateway), por quantos roteadores os pacotes passam até a NBA, e de quem é a rede onde o site da NBA está.

Tópico 4 — HTTP e HTTPS

O que são HTTP e HTTPS?

Onde estamos na viagem: os pacotes já chegam ao servidor da NBA e a conversa TCP está aberta. Falta pedir a página.

O que é HTTP. O HTTP (HyperText Transfer Protocol) é a língua da web: o combinado de como o navegador pede uma página e de como o servidor responde. Funciona como um pedido no balcão:

  • o pedido diz o que se quer (GET / = "me dá a página inicial") e traz cabeçalhos, como quem está pedindo (o User-Agent);
  • a resposta traz um código de status (200 = tudo certo, 404 = não existe, 403 = proibido), cabeçalhos e o conteúdo da página, em HTML.

O problema do HTTP. Ele viaja em texto aberto. Lembra dos roteadores de várias empresas no caminho (tópico 3)? Todos poderiam ler o que você pede e o que recebe, inclusive senhas.

O que é HTTPS. É o mesmo HTTP, dentro de um túnel criptografado, chamado TLS (o S é de secure, seguro). Ele garante duas coisas:

  • sigilo: quem está no caminho vê os pacotes passando, mas não consegue ler o conteúdo;
  • identidade: o servidor mostra um certificado digital, assinado por uma empresa confiável (a autoridade certificadora), que prova que ele é mesmo o nba.com. É isso que o cadeado do navegador confere.

Atenção: o cadeado prova que a conversa é segura com aquele site, e não que o site é honesto. Um golpista também consegue um certificado para o domínio falso dele.

Passo 3 — Novo: o User-Agent

Todo cliente se apresenta num cabeçalho chamado User-Agent. O curl se apresenta como curl/8.22.0; o Chrome, como Mozilla/5.0 …. A Akamai bloqueia clientes que parecem robôs. Vamos pedir de novo, apresentando-nos como navegador:

curl -I -A "Mozilla/5.0" https://www.nba.com

content-type: text/html; charset=utf-8
…
cache-control: private, no-cache, no-store, must-revalidate
date: Mon, 19 Oct 2026 16:40:42 GMT
  • -A (user Agent) = troca o User-Agent. Com Mozilla/5.0, a resposta passou a ser 200: deu certo.
  • "Mozilla/5.0" = o texto que o curl vai declarar. As aspas agrupam o texto (são obrigatórias quando ele tem espaços, como o User-Agent completo de um navegador). Por que "Mozilla"? Herança dos anos 1990: os sites mandavam páginas melhores para o Netscape (apelidado de Mozilla), e os outros navegadores passaram a se apresentar do mesmo jeito. Até hoje o Chrome, o Edge e o Safari começam o User-Agent com Mozilla/5.0.
  • Na saída: content-type: text/html; charset=utf-8 = página HTML com os caracteres (acentos inclusive) codificados em UTF-8; cache-control: private, no-cache, no-store, must-revalidate = "não guarde esta página, peça sempre uma nova" (é a página inicial, que muda o tempo todo); o … marca linhas omitidas aqui.
  • Ligação com segurança: sites usam o User-Agent para filtrar robôs (é um sistema antirrobô, parte de um WAF). Mas o User-Agent é só um texto que o cliente escreve, e é fácil mentir nele. Ele não prova a identidade de ninguém.

Tópico 5 — Cliente-servidor

O que é o modelo cliente-servidor?

Onde estamos na viagem: nos tópicos 1 a 4, nós fomos sempre quem pede. Agora vamos ver o outro lado: quem responde.

O que é. Quase tudo na internet funciona com dois papéis:

  • cliente: o programa que faz o pedido (o navegador, o curl, o app do celular);
  • servidor: o programa que fica esperando pedidos numa porta e responde (o site da NBA).

Servidor não é uma máquina especial. É só um programa escutando uma porta. Qualquer computador vira servidor ao rodar um programa desses, e é o que faremos com o Kali no passo 2. O mesmo computador pode ser cliente de um serviço e servidor de outro.

O servidor anota tudo. A cada pedido, ele registra num log quem pediu (o IP), quando, o quê e com qual programa.

Por que importa para segurança: os logs de servidor são a matéria-prima de uma investigação. E o que o cliente diz sobre si mesmo (como o User-Agent) é só uma declaração: pode ser falsa.

Aponte: a rede do laboratório foi criada com internal: true. Ela não tem saída para a internet. Mesmo que alguém errasse o alvo, nada sairia daqui. É assim que se monta um laboratório de segurança: fechado.

Passo 4 — Descobrir o IP da vítima

Dentro do laboratório, os contêineres se acham pelo nome. Para ver o IP por trás do nome vitima:

getent hosts vitima

Passo 6 — Novo: descobrir o software e a versão

nmap -sV -p 80,8000 vitima
PORT     STATE SERVICE VERSION
80/tcp   open  http    SimpleHTTPServer 0.6 (Python 3.14.8)
8000/tcp open  http    SimpleHTTPServer 0.6 (Python 3.14.8)
  • -sV: o -s agrupa os tipos de varredura (scan) e o V é de version. Além de "aberta", o nmap conversa com cada porta, compara as respostas com um banco de assinaturas e descobre qual software atende e qual versão (SimpleHTTPServer 0.6, Python 3.14.8). É o mesmo texto do cabeçalho Server: que vimos com curl -i no tópico 5.
  • -p 80,8000 (ports) = olhe só essas portas, separadas por vírgula (mais rápido). Também aceita faixas: -p 1-1000.
  • VERSION = a coluna nova na saída: o software e a versão.
  • Esta é a parte perigosa do reconhecimento. Sabendo o software e a versão exatos, o atacante procura falhas conhecidas daquela versão (slide 2). "Software desatualizado + versão à mostra" é o prato cheio.

Passo 7 — Novo: o ataque visto pelo DEFENSOR

Abra um segundo terminal e entre na vítima:

docker exec -it vitima bash

O mesmo docker exec do passo 2, agora entrando na vitima. Rode-o num segundo terminal do seu computador, fora de qualquer contêiner.

Veja o registro de acessos do site da porta 80:

cat /var/log/acesso.log
PedaçoO que significa
catmostra o conteúdo do arquivo (tópico 1)
/vara pasta de dados que variam com o uso: registros, filas, caches
/var/logonde ficam os registros (logs) do sistema e dos programas
acesso.logo log do site da porta 80. A receita do laboratório manda o servidor Python gravar ali cada pedido, no mesmo formato que vimos no tópico 5
172.23.0.3 - - [19/Oct/2026 17:46:40] "POST /sdk HTTP/1.1" 501 -
172.23.0.3 - - [19/Oct/2026 17:46:40] "GET /nmaplowercheck1792432000 HTTP/1.1" 404 -
172.23.0.3 - - [19/Oct/2026 17:46:40] "GET /HNAP1 HTTP/1.1" 404 -
172.23.0.3 - - [19/Oct/2026 17:46:40] "GET /evox/about HTTP/1.1" 404 -

Aponte, linha por linha:

  • 172.23.0.3 = o IP do atacante. O scan deixou rastro: a vítima sabe quem a sondou.
  • GET /nmaplowercheck…, /HNAP1, /evox/about, POST /sdk = a assinatura do nmap. Ele faz pedidos estranhos para adivinhar o software, e cada um fica gravado. Esses pedidos vêm do nmap -sV (passo 6); o nmap simples só bate na porta e vai embora, sem pedir página nenhuma.
    • /nmaplowercheck1792432000: uma página inventada, para ver como o servidor responde a algo que não existe. O número é a hora do scan contada em segundos desde 1970, o jeito como os computadores marcam o tempo.
    • /HNAP1, /sdk, /evox/about: endereços que só existem em aparelhos específicos (o /HNAP1 em roteadores domésticos, o /sdk em servidores VMware). Se a página existir, o nmap fica sabendo que tipo de máquina é.
  • 404 = Not Found: a página não existe. 501 = Not Implemented: o servidor do Python não sabe tratar pedidos POST.
  • A lição de defesa: todo scan deixa rastro. Quem monitora logs percebe que está sendo sondado — muitas vezes o primeiro aviso de que um ataque vem vindo.

Passo 8 — Novo: a defesa mais básica, fechar a porta

Ainda na vítima, desligue o serviço da porta 8000:

kill $(ss -tlnp | grep ":8000" | grep -o "pid=[0-9]*" | cut -d= -f2)

🔍 Entendendo o comando. É uma linha só, mas são 5 comandos encaixados. O $( … ) roda primeiro o que está dentro, e cada | passa o resultado para o comando seguinte, como no whois | grep do tópico 3:

EtapaO que fazO que sobra (exemplo)
1. ss -tlnplista as portas TCP que estão escutando (-t -l -n), com o programa dono de cada uma (-p)uma linha por porta, como LISTEN 0 5 0.0.0.0:8000 0.0.0.0:* users:(("python3",pid=8,fd=3))
2. grep ":8000"fica só com a linha que contém :8000a linha da porta 8000
3. grep -o "pid=[0-9]*"-o (only) recorta só o trecho que combina com o padrão: pid= seguido de algarismos ([0-9] = um algarismo; * = quantos houver)pid=8
4. cut -d= -f2cut corta o texto em pedaços: -d= usa o = como separador (delimiter) e -f2 pega o 2º pedaço (field)8
5. kill $( … )o $( … ) é trocado pelo resultado, e a linha vira kill 8: um pedido para o programa número 8 (o servidor da porta 8000) encerrar—

O número do processo (PID) vai variar. Para explicar mais devagar, faça à mão: rode ss -tlnp, leia o pid= da linha :8000 e rode kill com esse número. Volte ao terminal do atacante e escaneie de novo:

nmap vitima
Not shown: 999 closed tcp ports (reset)
PORT   STATE SERVICE
80/tcp open  http

Aponte: a porta 8000 sumiu do scan. Menos portas abertas = menos superfície de ataque. A defesa número um é simples: desligue e feche o que você não usa. O atacante só ataca o que consegue enxergar.
